# Fluent Next UI Kit

Мы собираем Figma UI Kit темы Fluent Next в файле **DevExtreme UI Kit (AI Generated)**. Каждый компонент
делается в своей Figma-ветке. Готовый компонент выглядит и ведёт себя как настоящий в демо, его свойства — это
API виджета, слои повторяют DOM. Каждое визуальное значение привязано к **компонентному токену**: переменной,
названной в точности как CSS-переменная Fluent Next (`--dx-button-height` → `button/height`). Значение токена —
алиас переменной из **Foundation tokens**, так же как во Fluent Next `--dx-*` раскрывается в `--dxds-*`.

Компоненты в ките уже есть, но их сгенерировали по старой теме Fluent, и значения в них захардкожены. Поэтому
работа в основном состоит в том, чтобы исправить существующее на месте, а не рисовать заново.

С пользователем говори на его языке. Это дизайнеры и разработчики кита, и каждое изменение они смотрят до мёржа
ветки.

## Что нужно до начала

- Подключён Figma Console MCP: один раз вызови `figma_diagnose`. Загрузи скилл `figma-console-routing`, а перед
  любым нетривиальным `figma_execute` — `figma-ai-cookbook`: его ловушки Plugin API относятся ко всему, что здесь
  делается.
- **Ветка** компонента открыта в Figma Desktop, и в ней запущен плагин Desktop Bridge. Нужна её ссылка
  (`https://www.figma.com/design/<mainKey>/branch/<branchKey>/…`). Если пользователь её не дал, спроси. Никогда
  не переключайся на основной файл вместо ветки.
- Демки работают на `http://localhost:8080`, Fluent Next в них собран. Если нет — [references/demos.md](references/demos.md).
- Для скриптов нужна Node 24.16+. Если `node -v` старше, добавляй перед командами
  `export PATH="/opt/homebrew/opt/node@24/bin:$PATH"`.

## Что уже решено

Эти решения согласованы с командой. Применяй их и не пересматривай. Подробности и примеры —
в [references/conventions.md](references/conventions.md).

1. **Имена токенов.** Имя Fluent Next без `--dx-`, префикс компонента вынесен в группу:
   `--dx-button-default-contained-bg-hovered` → `button/default-contained-bg-hovered`. Code syntax WEB у
   переменной — `var(--dx-…)`. Имён, которых нет во Fluent Next, не придумывай.
2. **Коллекции.** `theme` — один режим `fluent-next`, в ней цвета. `size` — режимы `default` и `compact`, в ней
   всё остальное. Светлая и тёмная тема — это режимы Fluent Light / Fluent Dark коллекции `Theme Switcher`
   из Foundation tokens, а не режимы `theme`.
3. **Значения.** `var(--dxds-a-b)` становится алиасом переменной Foundation `a/b` (`/` ↔ `-`). Ссылка
   `var(--dx-x)` становится алиасом локальной переменной `x`. `transparent` становится `color/none`. Всё
   остальное — пограничный случай.
4. **Свойства повторяют API дословно, в нижнем регистре:** `type=normal|default|success|danger`,
   `stylingMode=contained|outlined|text`. Состояния собраны в одно вариантное свойство
   `state=rest|hovered|focused|active|selected|disabled`, и в нём только те, которые тема действительно
   стилизует. Необязательные части названы по классам-модификаторам DOM (`hasIcon`, `hasText`). Если часть
   только показывается и прячется, это boolean. Если она меняет раскладку, это вариант. Содержимое задают
   свойства `text` (TEXT) и `icon` (INSTANCE_SWAP).
5. **Слои повторяют DOM по смыслу**, без лишних блоков. Имя слоя — класс элемента без `dx-`.
6. **Группы аннотаций `<Set> - Utils` не трогай.** Дизайнеры перегенерируют их своим плагином. Если сетка
   вариантов поменялась, напиши об этом в отчёте.
7. **Ветками распоряжаются дизайнеры.** Они сами создают ветки, сами обновляют их из main и сами мёржат. Задачи
   они тоже запускают явно. Ты работаешь только в выданной ветке и только над запрошенной задачей. Если для
   работы нужно действие с ветками (обновить из main, смёржить ветку другого компонента, подготовить main),
   скажи дизайнеру, что нужно и зачем, — но не делай этого и не начинай сам.
8. **Работа идёт по чек-листу** [CHECKLIST.md](CHECKLIST.md): снизу вверх по зависимостям. Скилл сам отмечает
   в нём «в работе» и «на ревью» и сразу пушит изменение в форк, чтобы дизайнеры могли работать параллельно.
   Подробности — в [references/checklist.md](references/checklist.md).
9. **Пограничные случаи обсуждаются до действий** (см. ниже).
10. **Решения пишутся в журналы мест.** Если пограничный случай решён через токен Foundation, место
    записывается в [DEV-HANDOFF.md](DEV-HANDOFF.md) — это для разработчиков. Если решён хардкодом — в
    [HARDCODED.md](HARDCODED.md). Скилл пишет и пушит оба журнала сам — см.
    [references/registries.md](references/registries.md).

## Порядок работы

Шаги 1–4 только читают. Пока пользователь не одобрил план из шага 4, в Figma ничего не меняется.

### 1. Предполётная проверка

- `figma_list_open_files` → найди ветку → `figma_navigate { url, lock: true }`. В ветке `figma.fileKey` — это
  **ключ ветки**, а `figma.root.name` — имя ветки. Каждый скрипт проверяет этот ключ. Если пользователь
  указывает на основной файл кита, остановись и попроси ветку.
- В ветке уже должны быть коллекции `theme` [fluent-next] и `size` [default, compact] и подключена библиотека
  Foundation tokens. Если коллекции нет, значит main не подготовлен. Создать её в ветке нельзя: при мёрже
  получится дубль. Остановись и объясни ситуацию — см. [references/figma.md](references/figma.md#ветки-и-коллекции).
- Проверь компонент в чек-листе: `node .claude/skills/fluent-next-ui-kit/scripts/checklist.mjs show <компонент>`.
  - Если он уже «в работе» по другой ветке, им занимается кто-то другой. Остановись и спроси.
  - Если не всё из «Состоит из» смёржено, это пограничный случай. Назови, чего не хватает.

### 2. Разбери компонент в коде

```bash
node .claude/skills/fluent-next-ui-kit/scripts/component-tokens.mjs <widget> --spec <scratchpad>/<widget>.spec.json
```

`<widget>` — папка виджета во Fluent Next (`button`, `checkBox`, `textEditor`, …). Скрипт печатает:

- все опубликованные токены, их коллекцию и тип;
- значения для default и compact;
- кто читает токен: селектор и CSS-свойство в собранном CSS — отсюда видно, к какому слою и полю его привязывать;
- флаги пограничных случаев.

Ещё он пишет спецификацию для шага 5.

Многие виджеты составные: TextBox — это `textEditor` + `textBox`, кнопки DropDownButton берут токены `button`.
Поэтому запускай скрипт для каждой части, которую рисует Figma-компонент. Потом прочитай API
`packages/devextreme/js/ui/<widget>.d.ts` — нужны опции, которые меняют внешний вид. Где искать остальное —
[references/sources.md](references/sources.md).

### 3. Посмотри на живой компонент

Открой демки виджета с темой Fluent Next ([references/demos.md](references/demos.md)) и зафиксируй:

- структуру DOM;
- вычисленные стили в покое и в каждом состоянии (состояния форсируются классами `dx-state-*`);
- compact и тёмную тему;
- скриншоты для финального сравнения.

Если демка расходится с таблицей токенов, верь демке: это то, что видит пользователь. Само расхождение запиши
как пограничный случай.

### 4. Проинвентаризируй Figma-компонент и составь план

Запусти аудит набора компонентов в ветке:

```bash
node .claude/skills/fluent-next-ui-kit/scripts/figma-code.mjs audit --file-key <branchKey> --node <setId>
```

Команда печатает код для `figma_execute` (`fileKey`, `timeout: 30000`). Аудит показывает:

- свойства и недостающие комбинации вариантов;
- дерево слоёв варианта по умолчанию с привязками;
- все непривязанные значения, сгруппированные по слоям;
- привязки в обход компонентного слоя;
- страницы, где живут инстансы.

Потом дай пользователю один короткий план и дождись явного «да»:

- **Токены:** сколько создать в `theme` и в `size`, какие отложены как пограничные.
- **Свойства и варианты:** старые → новые имена и значения, какие состояния добавляются или убираются,
  сколько вариантов получится.
- **Слои:** что переименовывается, складывается или добавляется.
- **Инстансы под риском.** Аудит даёт:
  - страницы и количество;
  - в мастерах каких компонентов лежат инстансы;
  - какие у инстансов переопределения: сырой цвет, фиксированный размер, шрифт.

  Скажи, что с каждой группой будет. Переопределения и инстансы в чужих мастерах — пограничные случаи.
- **Пограничные случаи:** у каждого варианты решения, рекомендуемый первым
  ([references/edge-cases.md](references/edge-cases.md)).

### 5. Запиши токены

Сначала, как только план одобрен, отметь компонент в чек-листе. Команда сразу пушит изменение:

```bash
node .claude/skills/fluent-next-ui-kit/scripts/checklist.mjs set <компонент> in-progress --branch <url ветки>
```

Потом запиши токены:

```bash
node .claude/skills/fluent-next-ui-kit/scripts/figma-code.mjs upsert --file-key <branchKey> --spec <spec.json>
```

- Сначала реши пограничные случаи: в их записях спецификации замени `unresolved` на `ds`, `link` или `value` и
  убери `skip`.
- Выполни код. Скрипт идемпотентный и сообщает, что создано, обновлено, не изменилось, пропущено и где были
  проблемы. Прочитай `problems` и `unresolvedDs`, прежде чем идти дальше.
- Большой виджет дели на части через `--only '<regex>'`, если вызов подходит к лимиту в 30 с.
- Ссылка на токен другого компонента, которого ещё нет в main, придёт в `problems`. Это пограничный случай,
  создавать такой токен здесь нельзя.
- Каждый токен, который по решению пользователя стал алиасом Foundation в обход кода или получил сырое
  значение, сразу запиши в журнал: `registry.mjs add foundation …` или `registry.mjs add hardcoded …`
  ([references/registries.md](references/registries.md)).

### 6. Пересобери компонент на месте

Правь существующий набор, чтобы его инстансы по всему файлу остались связаны. Правила и рецепты кода — в
[references/figma.md](references/figma.md):

- Свойства и значения переименовывай, переписывая имена вариантов. Имена должны остаться уникальными.
- Слои переименовывай на месте. Переопределения в инстансах (текст подписи, подмена иконки) держатся за слой,
  а не за его имя. Слой, который переопределяют инстансы, не удаляй и не пересоздавай.
- Недостающее состояние добавляй клонированием варианта внутрь набора, затем перепривязывай его.
- Вариант удаляй только после того, как его инстансы переведены на другой.
- Привяжи к токенам компонента каждое визуальное значение:
  - заливки, обводки, толщины обводок, радиусы;
  - отступы, промежутки, фиксированные размеры;
  - у текста — размер, начертание, гарнитуру, интерлиньяж и межбуквенный интервал.

  Таблица соответствий — в [references/conventions.md](references/conventions.md#привязки).
- Вариант по умолчанию (значения API по умолчанию) поставь левым верхним.
- Поле, которое по решению привязано к Foundation напрямую (начертание текста, стиль тени) или оставлено без
  привязки, сразу запиши в журнал так же, как токены в шаге 5.

### 7. Проверь

- Повтори аудит. Из непривязанных групп остаться могут только согласованные пограничные случаи. Привязок
  `library` и `other-local` быть не должно, если о них не договорились.
- Сверь аудит с журналами: `registry.mjs list --component <компонент>`. У каждой оставшейся непривязанной группы
  должна быть строка в HARDCODED, у каждой привязки `library` — в DEV-HANDOFF. Нет строки — значит, решение
  пропущено: допиши.
- Собери временную превью-рамку на странице компонента: инстансы всех состояний с явными режимами переменных
  (Theme Switcher Fluent Light / Fluent Dark × size default / compact). Положи скриншот рядом со скриншотами
  демки и сравни размеры, цвета и отступы. Потом удали рамку.
- Убедись, что инстансы на других страницах (из аудита) по-прежнему отображаются и сохранили свои
  переопределения.

### 8. Отчитайся

В отчёте по порядку:

1. Что изменилось: какие токены созданы и обновлены, что стало со свойствами, вариантами и слоями.
2. Пограничные случаи и как решён каждый.
3. Какие строки добавлены в DEV-HANDOFF и HARDCODED.
4. Что осталось сделать.
5. Нужно ли перегенерировать аннотации Utils.

После отчёта отметь компонент в чек-листе:

```bash
node .claude/skills/fluent-next-ui-kit/scripts/checklist.mjs set <компонент> review --note "<одна строка: что сделано, что осталось>"
```

Мёрж ветки делают дизайнеры. Сам ничего не мёржи, не обновляй ветку из main и main не трогай. Когда
пользователь скажет, что ветка смёржена, поставь `merged`. На вопрос «что брать дальше?» отвечает `next`.
Если пуш чек-листа не прошёл, скажи пользователю, что именно, и не пушь в другое место сам.

## Остановись и спроси

Пограничные случаи пользователь хочет обсуждать до того, как с ними что-то сделано. Пограничный случай — любое
место, где правила выше сами по себе не определяют результат:

- флаг скрипта;
- расхождение демки и токенов;
- значение без токена;
- опция API, которая не ложится на свойство однозначно;
- изменение, которое сломает инстансы;
- зависимость от ветки другого компонента.

Собери их, к каждому предложи конкретные варианты решения (рекомендуемый первым) и жди ответа. Известные случаи
с обычными вариантами решений и журнал **Решено** — в [references/edge-cases.md](references/edge-cases.md).
Если решение повторится в других компонентах, допиши его в журнал, чтобы на следующем компоненте не
переспрашивать.
